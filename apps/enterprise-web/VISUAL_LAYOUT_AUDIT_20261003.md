- 空搜索框、提醒事项、日期时间、模型下拉已有常态边框；新 web 控件最小高度 42px，聚焦轮廓清楚。无需再报“只有文字看不到输入框”。

## A. 可确认的布局问题

### V-01 · P1 · 提醒中心的待办被低频配置挤出常见笔记本首屏

**证据**：1366×768 截图中，从页头到创建区起点约占 280px，两个折叠历史入口和声音配置先于任务收件箱出现。统一任务收件箱在画面底部才开始，个人提醒更靠后。`shared/assistant-reminders.tsx:340` 先渲染 history、声音配置，再渲染创建表单与收件箱；不是数据缺失。

**建议**：提醒中心首层分“待处理任务”“新建提醒”，默认先展示待处理任务；触发历史、投递记录、声音放到一行的“通知设置与记录”折叠区。保留一键新建入口和声音开关，不改变提醒触发规则。页面区块间距 20–24px；折叠设置行高 40–44px，避免两条折叠标题分别占 70px 视觉高度。

**验收**：1366×768 下，进入页面不滚动即可看到筛选与至少一条待办；空列表也有明确空状态。切换创建不丢已有草稿；历史和声音可用键盘访问。改信息顺序需确认，不混入金额/提醒业务修改。

### V-02 · P1 · 网页提醒页仍沿用弹窗高度约束，形成第二层页面滚动

**证据**：`shared/enterprise-client.css:12–18` 的 inline 提醒区 `max-height:calc(100dvh - 180px); overflow:auto`，而 `.hesc-main` 在 `:422` 自身也是 `overflow:auto`。1366 截图的整块内容在 y≈714 处截断，固定底栏在 y≈728；960×540 图仅有约 360px 提醒内部视窗。控件能滚到，不应描述为永久不可操作。

**建议**：仅对网页 inline 页面取消弹窗式 max-height/overflow，以主内容区作为唯一页面纵向滚动；真正弹窗仍保留 `max-height:calc(100dvh - 32px)`。长任务列表使用分页或明确列表滚动，不让“页面→表单大卡→任务列表”同时争夺滚轮。

**验收**：鼠标位于标题、表单、列表空白处时滚动方向一致；Tab 聚焦最后一项不会藏在底栏下；个人提醒任务可处理，真正单任务弹窗关闭后仍恢复来源位置。

### V-03 · P1 · 960px 临界宽度仍使用完整侧栏，并保留提醒左右双列

**证据**：960×540 图侧栏为216px，内容区只剩约744px；CSS `:2242` 用严格 `width < 960px`，恰好960px不折叠。提醒双列要到840px才变单列（`:54`），此时右侧手动提醒约280px宽，日期/时间已分到上下，创建按钮仍在下方。1920显示器200%时可能进入这一有效宽度，需真实缩放验收。

**建议**：网页在有效宽度≤1100px或内容宽度不足900px时折叠导航；保留可访问名称/可打开文字导航。提醒布局按内容宽度切换：不足800–880px改为单列或“自然语言/手动”两种创建方式切换，不仅按全窗口840px判断。

**验收**：960×540、959×540、1024×768 连续调整无突然挤压；真实1920×1080@200%及1366×768@200%可看到选中导航、填写日期时间并提交/取消，不能仅通过document横向不溢出就算通过。

### V-04 · P2 · 手动提醒日期与时间在宽屏被拉到两端，字段组合感弱

**证据**：1920截图右侧面板宽约600px，日期靠左、时间靠最右，中间留约300px；1366时同一组合又挤窄。标签和输入已经有边框，本项不是控件可见性旧问题。

**建议**：日期/时间使用局部 `grid-template-columns:minmax(160px,1fr) minmax(110px,.65fr)`、间距12–16px，输入宽100%；表单内容建议最大宽560px；创建/清草稿在一行就近排列。容器不足340px时整组单列，不分散到两端。

**验收**：1920和1366中日期与时间被读为同一“提醒时间”组合；键盘顺序为事项→日期→时间→创建；窄宽度不裁切原生日历/时钟图标。

### V-05 · P2 · 应收统计的十张等权卡片与每日区，使对应任务阅读入口过深

**证据**：当前应收截图1280×900下，首屏主要是标题、查询、说明与十张统计卡，任务明细尚未出现。`web/receivables-data.ts` 有十项指标，`shared/receivables-report.css:1` 统一180px最小卡宽；已有点击后滚动，不能再报“点击未映射”。

**建议**：保留用户要求的金额映射：首层突出“当日待收/未收总额/逾期未收/已确认收款”4项；其余“金额组成与账龄”折叠展开，同样可点击。或保留十项但分主要金额与账龄两组，用主卡96–112px、次卡64–80px高度。每日金额区默认7天，列表最大280px可保留。

**验收**：主要指标仍稳定，不受当前明细分页或单项选择影响；任何指标点击仍选中同一明细区域，不引入第二个任务列表；不将关闭/取消未收隐藏出统计口径。此项为信息层级调整，应在实施前确定布局方案。

### V-06 · P2 · 金额表格缺少数字列对齐，长业务对象仅省略不利于区分

**证据**：`web/receivables-overview.tsx` 应收、已收、剩余均为普通td；共享表格没有金额列专属右对齐。`shared/enterprise-client.css:804` 全部第一列 `max-width:0; white-space:nowrap; text-overflow:ellipsis`，新应收第一列未提供完整名称提示。截图短名字正常，不代表长同前缀群名可区分。

**建议**：金额列右对齐、tabular-nums、2位小数原样展示且币种就近；业务对象列允许两行，团队/负责人降低一档权重；长名字提供可键盘访问的完整名称或进入详情后清晰主标题。表格在窄屏保留自身横向滚动，不能省略关键金额列来“通过”溢出检查。

**验收**：用1.00/1234567.89、两条前30字相同的群名、8–9列历史表测试；金额小数点方向一致，长名字能无歧义识别，列表金额与详情值一致。不改金额计算/舍入规则。

## B. 可选优化及待复测风险（不能称为已确认生产故障）

### V-07 · P2 · 网页外壳保留原生客户端空间，可回收垂直工作面积

**证据**：token为标题栏44px+顶部56px+底栏40px；网页截图同时重复企业服务连接状态。`shared/enterprise-client.css:170` 标题栏右侧固定164px padding是Electron按钮预留，网页并无这些按钮；这是已确认空间使用，可否去掉属于设计选择。

**建议**：网页合并品牌/租户/账号到56–64px单顶栏，底部连接详情按需展开，或底栏压缩为24–28px。不要删掉账户安全、通知与异常状态入口。只做网页覆盖，不改变原生窗口标题栏。

**验收**：1366×768可增加至少44px业务视窗；失联异常始终可见；正常状态不在三处重复抢注意力。

### V-08 · P1风险 · 窄宽聊天仍有720px最小高度，200%缩放输入区需专测

**证据**：`shared/enterprise-client.css:1996–2000` 在宽度<1100px设置聊天转为单列、历史最多188px、transcript最小720px；输入区在transcript尾部。源码约束可确认，但本审查没有跑真实缩放后的聊天截图，不能声称发送按钮不可达。

**建议**：窄宽网页按可用高度布局，历史用折叠抽屉；聊天历史滚动、输入区固定在工作区底部但不覆盖内容。若选择自然文档流，取消720px硬最小高度，并提供明显“回到输入”而非留大段空白。输入框默认约96px，增长上限160–200px。

**验收**：1920@200%、1366@200%，空对话/长回复/多轮/输入多行都能找到发送；浏览器缩放不把工具栏或历史挤成多屏；不能仅以页面无横向滚动验收。

### V-09 · P1风险 · 长标题提醒toast没有宽度上限，可能覆盖表单或超出窄视窗

**证据**：`shared/enterprise-client.css:29` 固定right24/bottom42、flex无max-width；现有明细截图toast已覆盖新建表单右下部分。真实长任务名/200%没有测试，不据此断言所有提醒都遮挡提交。

**建议**：网页toast宽 `min(480px,calc(100vw - 32px))`，标题两行省略并支持详情，主体可换行，操作不缩小；窄屏上下排列，右16px。不能改变通知时机、声音、30分钟再次提醒或业务状态。

**验收**：100字群名与英文连续字符，1366@200%、960px均不横向溢出；“稍后处理”仍可点；与详情弹窗同时出现时不盖住唯一确认/取消动作。

### V-10 · P2 · 角色工作台目前主要靠标题文案区分，可调整视觉优先级

**证据**：`shared/role-presentation.ts` 已区分我的/团队/运营工作台；`shared/app.tsx:224` 仍复用相同四张顶层状态卡。不是角色权限缺失，业务权限另由专门审查负责。

**建议**：员工先放“我的待处理/今日待收”，主管先放“团队逾期/待审核”，管理员先放“本企业应收/逾期/审批”，技术健康与能力数收至次级。金额与任务卡标题标明本人/团队/企业范围；卡片显隐必须复用已授权数据和服务端范围，不根据视觉角色推导新权限。

**验收**：每个角色首屏至少包含该角色首要工作入口；不因重排暴露企业全量金额；无权限数据不能显示为0；不同角色截图分别验收。

## 尺寸基线建议

这些是可执行目标，不是对现状已合规的声明，也不是要求所有控件强制同一尺寸。

| 项目 | 建议范围 | 备注 |
|---|---|---|
| 正文 / 表格 / 主回复 | 15–16px，行高24–28px | 当前字号已接近，不必全局再放大 |
| 辅助说明 | 13–14px，行高20–22px | 关键金额/状态不能降为辅助字 |
| 页面 / 区块标题 | 26–28px / 17–20px | 提醒页标题应与其他页面形成同级层次 |
| 普通输入 / 主要按钮 | 40–44px | 主任务42px输入可保留；密集行按钮另行评估 |
| 卡片 padding / 区块 gap | 16–20px / 20–24px | 避免每层容器重复20px导致窄屏可用宽度不足 |
| 搜索框 | 常规280–360px，窄屏100% | 不恢复空值透明 |
| 财务主卡 / 次卡 | 96–112px / 64–80px | 大金额不拆成任意位数换行 |
| 单任务弹窗 | 最大1000px，距视窗至少16px | 保留自己的纵向滚动、焦点与来源恢复 |

## 补充验收矩阵

1. 1920×1080、1366×768、1024×768、960×540、959×540；真实浏览器200%缩放，不仅设置viewport或deviceScaleFactor。
2. 管理员/主管/员工分别看首屏；只用隔离夹具或明确授权测试账号，不对生产应收款做试写。
3. 0条/1条/100条任务、100字群名、多币种、大金额、多行说明、接口失败/加载；不能用全空夹具证明密集布局正常。
4. 可视范围测试针对各scroll容器的交集，而非只测试document.scrollWidth；记录按钮是否被固定栏/toast遮挡。
5. 键盘Tab到页末、表格操作、折叠展开、弹窗Escape、关闭后来源焦点；后台刷新不得抢滚动。
6. 原审查已修控件不回退；金额映射、历史口径、角色权限、提醒次数/音频均不能因视觉整改变化。

## 建议顺序

先处理V-01/V-02/V-03并专测V-08/V-09；接着V-04/V-06。V-05/V-07/V-10属于较大信息层级或布局选择，建议先提供局部线框给用户确认，避免在“补齐旧审查”中悄悄大改工作习惯。所有项只建议网页版，不自动更新客户端。
