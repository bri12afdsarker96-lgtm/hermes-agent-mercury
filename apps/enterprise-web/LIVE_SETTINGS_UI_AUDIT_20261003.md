# 网页端设置与管理入口：线上只读 UI 审查

审查日期：2026-10-03。对象：https://ppbb096.site/ 新建独立浏览器标签页（企业管理员会话）。本报告只涉及网页，不评价或修改客户端。

## 结论与边界

结论：**HOLD，尚不能作为“各入口全量体验已对齐”的验收依据。** 主要阻断不是配色，而是人设/知识记录难以辨认、长列表挤压布局、通知入口与实际内容不匹配。当前已实见的表单边框比用户早期截图清晰，但这不等于所有工作流可用。

采用 agency-agents 的 UI Finish-Gate Reviewer 与 UX Researcher 方法：以真实呈现、任务顺序、可识别性、逐步展开和证据覆盖审查，不用源码代替页面观察。此次为专家走查，不是用户访谈或可用性实验，没有编造用户完成率。

执行约束：只导航、展开、切换只读筛选与滚动；未修改真实数据、配置、权限、密码，未发送测试通知，未读取或输出密钥。未点击会生成绑定码的绑定操作，未提交上传、审批、删除、保存。管理员删除任务修复由主线处理，不包含在本报告修复结论内。

证据形式：本次浏览器工具会话中的实际截图及对应 DOM 快照。以下 E 编号是本报告的观察索引，不是磁盘截图文件。截图外侧出现的白色区域可能与浏览器截图缩放有关，未将它认定为网站缺陷；文中像素均为画面估算，不是 CSS 测量。页面未直接显示部署构建号，因此不据此断言精确版本。

## 逐项整改建议

优先级：P1=严重妨碍核心识别/易误选；P2=明显交互、映射或可用性问题；P3=文案与一致性优化。建议改变展示层时保留现有权限和业务规则，不通过删功能解决问题。

### S01 / P1 人设名称被挤到无法辨认

- 位置/证据：AI模型配置→人设，E07 底部表格。名称表头折行，三行名称只剩一个字加省略；长“适用说明”几乎占满整表。
- 影响：管理员难以确认正在设为默认、编辑或删除哪一个人设；这比普通字号问题风险更高。
- 建议：名称列至少容纳 8–12 个汉字，建议最小 160px；默认标签紧随名称。适用说明默认两行省略并提供“查看说明”，完整人设设定在详情/编辑中呈现；操作固定宽度。
- 验收：现有三个名称在桌面视口不截成单字；长说明不能继续压缩名称列；默认人设无需打开详情即可明确识别。

### S02 / P1 知识记录缺乏可用于业务识别的摘要与搜索

- 位置/证据：E01。页面显示已发布资料规模 7782 条；当前列表一页 100 条，其中绝大部分同名“直播与达人招商”，靠六位编号区分；没有可见关键词搜索。
- 影响：管理人员只能连续点击辨认，难以定位具体知识；批量选择时容易混淆。不能据同名认定数据重复，问题在识别信息不足。
- 建议：列表主标题采用具体问题/条目标题，主题改为次级分组；补充一行标准问题或内容摘要。增加关键词查询及主题/状态过滤；编号移至次级信息或详情，不让它充当主要辨别线索。
- 验收：输入一条已知标准问题可定位对应记录；同主题多条知识无需逐条打开即可区分；只显示当前授权范围的搜索结果。

### S03 / P2 知识双栏被最长列表拉伸成多屏空白

- 位置/证据：E01 中段及尾部。左侧列表滚动数屏后，右侧第一条详情内容已消失，留下贯穿多屏的空卡；分页只在 100 条末尾。
- 影响：阅读位置丢失，名单与详情失去对应关系，页面长度受条数放大。
- 建议：队列固定合理视口高度、内部滚动，详情独立滚动或粘性定位；分页提供当前页/总量与每页数量，在可见底栏固定。避免强制详情高度等于整份列表高度。
- 验收：100 条数据时仍能在一屏内看到所选条目与详情开头；滚至队列末尾不出现几屏无内容的详情卡；分页无需滚过全部条目才能操作。

### S04 / P2 知识批量操作与空状态不匹配

- 位置/证据：E02，待审核零条时仍有“选择本页待处理”“选择本页知识”；空右栏仍要求选择资料。
- 影响：没有对象却出现可点选择，增加无效操作；两个选择命令也不易区分。
- 建议：空结果时隐藏或禁用批量选择；显示“暂无待审核资料”。有数据时用带计数的统一复选框“全选本页（N）”，仅有不同语义确有必要时再展示“仅选待处理”。
- 验收：零条无可执行批量动作；已选数量、可处理数量可见；切换状态后不残留不在结果中的选中项。

### S05 / P2 上传历史暴露内部英文状态

- 位置/证据：E03 历史上传表，状态直接显示 `staged`、`edited`。
- 影响：用户无法判断是否上传成功、是否需要审核；与知识列表中文状态不统一。
- 建议：先核对业务含义后映射中文，如“待提交”“已编辑，待提交”；不要未经核对把 edited 当作已审核。诊断值留内部，不常驻业务界面。
- 验收：每一种状态都有唯一中文名称及正确下一步；同一批次在上传历史、审核列表和详情中的阶段不互相矛盾。

### S06 / P2 上传历史列宽反向分配，文件分册难以分辨

- 位置/证据：E03。文件名列画面约 170px，而时间与操作列分别占很大宽度；同前缀分册名大量省略，难以看到“分册1/2/3”。
- 影响：恢复错误上传批次的概率上升。
- 建议：文件名占可用宽度至少 40%，允许两行并保留尾部扩展名/分册；时间约 180px、状态约 100px、操作约 120px；悬停及键盘聚焦可查看完整文件名。
- 验收：现有长文件的分册标记可直接区分；时间不占半表；各行“继续处理”与对应文件保持明确对齐。

### S07 / P2 历史上传展开后遮蔽主任务

- 位置/证据：E03，23 条历史在上传表单之前展开，表单和生成预览动作被推至几屏下方。
- 影响：进入“上传知识”后先看历史而不是上传；未完成任务和新上传混在一条长路径。
- 建议：上传表单在前，历史放后或独立“上传记录”子页；历史限高或分页。保留“恢复未完成上传”入口，不删除历史能力。
- 验收：无论历史是否展开，上传文件和主题输入在首屏可达；历史列表有明确数量与分页/滚动边界。

### S08 / P3 知识入口与说明重复

- 位置/证据：E01/E03/E04。全局“上传文件”与“上传知识”分区并存；发布可问答提示在标题、状态及侧栏重复；空缺口页长句解释审核发布流程。
- 影响：主次入口不集中，已熟悉的流程每次占据视线。
- 建议：统一主按钮“上传知识”；常态只保留状态“已发布”。缺口空状态用“暂无待补充问题”，可附“上传知识”。**文件格式、预览审核要求不可直接删除**，放在“格式与发布说明”展开项。
- 验收：上传只有一个明确主动作；发布前必须审核的信息在真正提交前可见；业务知识正文不因“简化文案”被修改。

### S09 / P2 回复服务配置同名记录无法区分

- 位置/证据：E06，高级设置下两条均为 deepseek / deepseek-chat，仅默认标记不同。
- 影响：更新或删除非默认配置时无法知道是哪份配置；不能据此直接判定后端重复或错误。
- 建议：增加配置名称/用途及非敏感的验证状态，必要时最近更新时间；不要回显密钥。标题可统一为“回复服务”，新增按钮用“新增配置”，在默认知识检索页保持低存在感。
- 验收：相同厂商和模型的两份配置仍可凭名称区分，选中行在编辑标题中持续显示；默认保护不改变。

### S10 / P2 人设新增抢占空间，默认状态提示互相冲突

- 位置/证据：E07。人设页新增三字段表单默认展示，现有人设名单位于下面；已有默认标签仍出现“请指定默认人设”。
- 影响：最常见的查看/切换现有人设必须先越过新增；文案让管理员误以为默认尚未配置。
- 建议：名单在前，“新增人设”按需展开；已存在默认时显示“默认：销售顾问”，无默认才提示设置；长设定只在编辑中展示。
- 验收：初次进入可直接看到现有人设与默认项；有默认时不出现缺默认指令；创建流程仍完整。

### S11 / P2 员工列表缺少查询与团队上下文

- 位置/证据：E08，约二十余名员工在固定高度表格内；有姓名、账号、角色、状态、操作，无搜索/组别筛选与组别列。
- 影响：识别人时需要反复滚动，查团队归属需要换到组别页；与其他模块的“先团队后个人”路径脱节。
- 建议：表格上方提供姓名/账号搜索、团队筛选、角色筛选；列中显示组别，团队选定后人员范围只在该团队内。与组别页复用同一归属数据。
- 验收：指定团队后列表无其他团队人员；姓名/账号查询覆盖当前权限内全部页，不仅已载入可见行；清空筛选恢复列表。

### S12 / P2 员工管理界面被删除动作主导

- 位置/证据：E08，非管理员各行最显眼操作是红色“删除账号”；上方常驻一整段永久清除关联数据的说明。
- 影响：危险低频操作压过日常管理，长提示又容易被习惯性忽略。
- 建议：删除放入行内“更多”或次级危险操作区；永久删除影响必须保留在确认框，列出当前目标与影响范围。角色职责放“权限说明”，首次改密码提示放开通成功交接信息。
- 验收：列表主视觉不再整列高亮红块；进入删除确认时目标、不可恢复性、关联数据后果完整可见；不新增或扩大权限。

### S13 / P2 组别页面默认全量编辑，日常成员管理藏在底部

- 位置/证据：E09。8 组每行约 140px，组名重复显示为标题和输入值；各行常驻编辑组名/保存/删除，坐席归属表在所有组别之后。
- 影响：查看团队与成员需要穿过两屏编辑表单，屏幕高度被低频修改消耗。
- 建议：用紧凑组别名单/卡片展示组名、负责人、人数；点组后在旁边或下方显示该组成员；“编辑组别”再打开表单。创建组别也可按需展开。
- 验收：首屏看到团队与对应成员入口；选组直接得到该组坐席；未进入编辑态不显示每行保存按钮；原删除/归属规则保留。

### S14 / P2 调整归属的提交语义不明确

- 位置/证据：E09 底部归属表，当前组别和“调整归属”下拉并排；没有对应保存/确认说明。与上面的组名明确“保存修改”模式不同。
- 影响：用户不知道选择即保存还是仅选中草稿。本次没有改变选项，**不对实际自动保存行为下结论**。
- 建议：统一为“调整归属”对话框，先明确原组→目标组再确认；如确为即时保存，应显示轻量明确说明与成功反馈，并在涉及可见范围变化时确认。
- 验收：在测试数据上验证取消不更改归属，成功与失败反馈明确；组别人数、人员筛选、角色可见范围同步一致。

### S15 / P3 待审批空状态仍常驻内部交接机制

- 位置/证据：E10。暂无申请，但仍说明批准后行移除、管理员不见初始密码、申请主管一次性查看等。
- 影响：当前没有任务，规则说明成为页面主体；“主管坐席申请”也容易误读为主管自己的席位。
- 建议：标题“坐席开通申请”；空状态“暂无待审批申请”。密码交接规则放“审批说明”或批准结果，不删安全约束。
- 验收：空状态简洁；审批前后仍能找到密码接收人和一次性查看规则；有申请时一眼看到申请人/主管/目标团队。

### S16 / P2 “通知设置与记录”没有记录展示，与“系统通知”含义混淆

- 位置/证据：E12 未绑定账号，仅一张企业微信绑定卡，没有通知记录或其空状态。E14 顶部“系统通知”只显示浏览器权限说明，也不是通知列表。
- 影响：用户到两个看似记录/消息入口，都找不到通知记录，不知道是无记录还是尚未实现/未绑定才隐藏。
- 建议：顶部改“桌面通知设置”或“通知权限”；工具子页改“我的通知”，分“接收方式”“通知记录”。无记录也给明确空状态；若当前确不提供记录，直接从标题去掉“与记录”，不要用不存在的功能命名。
- 验收：入口名称与实际内容一一对应；未绑定状态可理解哪些通知仍可接收；通知记录是否受绑定影响有明确表现。已绑定真实记录仍需后续安全样本验证。

### S17 / P2 企业微信绑定文案指向不一致

- 位置/证据：E13 文案“谁创建提醒，谁在‘提醒中心’绑定自己的企业微信一次”，而本次实际看到绑定按钮在工具集→通知设置与记录。
- 影响：配置者让员工去错位置。未据此断言提醒中心绝对没有第二入口，但现有说明未指向此次可见入口。
- 建议：短句“成员绑定企业微信后可接收个人提醒。”附真实可点击“去绑定”；若多个入口允许存在，统一跳到同一绑定界面。
- 验收：点击文案入口直接到本人绑定状态，不能打开企业级密钥配置；路径在各角色可用且不越权。

### S18 / P2 通知渠道分区与尺寸层级不合理

- 位置/证据：E13。群 Webhook 与个人应用配置放同一长卡，上一段保存按钮紧贴下一段标题。七个字段都约 420px 单列，右侧大片空白，最后保存按钮要滚动才能看到。
- 影响：两种接收方式的关系不清楚，配置成本高，保存作用域容易误读。
- 建议：拆成“群通知”“个人通知”两个独立折叠卡，先状态后“配置”。展开后表单限制在合理宽度（约 720–900px），标识字段两列、密钥长字段整行；各卡独立保存区。为 CorpId/AgentId 等提供精简中文标签+必要技术名，不把必需参数藏没。
- 验收：每个保存按钮明确仅保存所属渠道；完整表单无不必要长滚动；未配置时不默认暴露全部高级字段；密钥继续不回显。

### S19 / P2 账户安全未操作就报错

- 位置/证据：E15。初次打开三个空字段，立即显示红色“请输入当前密码”“新密码至少6位…”“两次输入…必须一致”。没有输入或点击提交。
- 影响：用户在未操作时已进入错误态，难以分清规则提示与真实错误。
- 建议：初始规则用中性辅助文本，仅 blur 后相关字段或提交后展示校验错误；顶部与新密码字段重复规则只保留一份。关于清除记住密码的说明保留在成功反馈/底部简短提醒。
- 验收：首次打开没有红色错误；实际错误才红色标记并关联字段；密码空值不可提交，现有安全规则不削弱。本次未进行密码验证或变更。

### S20 / P3 本地工具说明可以精简，但隐私承诺应保留

- 位置/证据：E11，未外呼订单筛选首屏连续算法说明、隐私说明、文件限制，文件选择各占一行。
- 影响：实际两步选文件的操作被数段文字分隔。
- 建议：用“1 选择外呼记录（1–20份）”“2 选择订单总表”“生成未外呼订单”组织；默认一行“仅本地处理，不上传”；格式/去重/前导零/容量限制进入“文件要求”展开项或控件附近。不要把订单号文本处理能力删掉。
- 验收：不读整段说明也知道两份输入区别；文件限制在选择前可见或可展开；本地处理和不上传的事实仍明确。

### S21 / P3 通知权限弹窗应给状态而非解释为主

- 位置/证据：E14，弹窗只有两段文字，权限已开仍详细解释自动播放、静音等。
- 影响：入口不提供可辨识的正常/异常状态，也无可控诊断步骤。
- 建议：默认“桌面通知：已开启”，保留重要边界“请保持网页打开”；故障说明收进“未收到提醒？”。可另评估人工点击“试听提示音/测试通知”，但测试动作必须由用户主动触发，不自动向真实业务发通知。
- 验收：正常状态一眼可见；关闭网页不保证送达的边界保留；不声称开启权限等于端到端送达已验证。

### S22 / P3 跨页按钮、分页与表单密度缺少统一规则

- 位置/证据：E02 知识空列表的上一页/下一页为近似裸文字，企业知识分区是大按钮，员工/工具分区为小标签；E08 空创建表单的按钮可用，而组别、上传、通知表单为空时禁用。
- 影响：同类状态的视觉语义不一致，用户需重新学习哪个是导航、哪个会提交。
- 建议：统一页签、主/次/危险/禁用按钮，分页使用可辨边框与页码；必填项有效性策略统一。员工空表单是否服务器拦截未验证，不能据“按钮可用”直接认定可创建空账号。
- 验收：各页签选中态一致；禁用按钮不只靠轻微色差；必填表单初始态不会提供看似可提交的无效动作或至少明确错误规则。

## 必须保留而不是一删了之的内容

1. 永久删除后果、权限范围、密码交接与凭据不回显等安全信息：放到真正决策点，不删规则。
2. 文件格式、审核发布前置条件、通知关闭网页后的边界：简化并渐进展开，不虚假承诺。
3. 企业知识中的业务正文：它是待管理数据，不是页面冗余介绍，不能因本次 UI 审查擅自删改。
4. 密钥/技术参数：仅在管理员主动展开配置时出现，不能为了“降低模型存在感”隐藏到无法配置或检查。

## 后续验证清单与证据缺口

- 本次只验证当前企业管理员视角。主管、坐席菜单可见性、接口授权与跨团队隔离必须用独立测试账号覆盖；不能从管理员页面推断权限安全。
- 用测试环境样本覆盖非空知识待审核、待发布、未通过审核、知识缺口及上传预览/继续处理；没有在生产环境生成资料来填充空状态。
- 人设新增/编辑、回复服务更新/新增的弹窗未打开；不能称内部表单已全审。
- 企业微信绑定会生成或使用身份凭据，未执行；已绑定通知记录及实际投递链路未验收。
- 文件筛选工具只观察空输入态，未验证导入、超限、前导零、生成结果；需用脱敏测试文件另验。
- 未操作密码、创建员工、调整归属、审批、删除等真实写入；需在隔离样本验证成功/失败/取消反馈与数据映射。
- 当前报告涵盖所列入口首中尾，并不是整个应用所有页面完成证书。运营总览、聊天、提醒、应收款和管理员删除由其他审查/主线负责。
