## 用户要求对应的目标流程

1. 页面最上方先显示金额卡及明确范围，例如“权限内全部 / 某团队 / 某坐席”。首次进入无需先填表。
2. 金额卡下方为团队下拉框，数据来自有权查看的组织组别，不再手填文本。
3. 团队后是该团队坐席下拉框；选择团队时默认“该团队全部坐席”，切换团队清空原人员选择并回到第一页。无坐席显示空状态，不能自动扩大到全企业。
4. 再提供业务对象/群名称、状态、日期等细分条件，随后显示对应任务。团队、人员切换建议直接生效；文本检索可保留查询提交，不混淆草稿条件与已应用条件。
5. 团队或人员改变后，金额卡和明细使用同一权限及筛选范围；点击金额卡只改变下方任务类别，不将其他卡片金额重算成该类别的局部值。保留现有 `summary_totals` 与明细选择分离的正确设计。
6. 切换当前/历史或金额类别时处理互斥状态，不能保留“已关闭 + 当前任务”一类隐藏矛盾。标题、选中卡片、筛选摘要和请求参数必须一致。
7. 运营总览金额跳转携带指标与币种，并明确落入的权限范围；人员与团队筛选不应在跳转后显示与实际查询不一致的旧值。

“团队”按用户所说的坐席组织归属理解，即员工与权限中的组别。历史文本业务团队不能直接假定等于组织组别；需保留旧标签并提供未关联记录口径，禁止通过模糊名称自动配组。人员调组后采用当前责任组还是创建时业务组，必须在接口字段上明确区分，不以名称替代稳定 ID。

## 不能直接复用管理接口的原因

`hermes_devices/webserver.py:2369` 的 `/api/operations-groups` 当前是企业管理员接口，且 GET 内有历史组别补齐与默认组创建行为。不能为下拉框简单开放此接口给所有角色，也不能将带写入副作用的 GET 当作本轮生产只读验证。

推荐扩展现有业务读取投影，返回当前业务权限内只读团队/人员选项，不带管理动作。团队和人员组合必须由服务端校验；前端下拉限制不是权限边界。

角色约束：管理员看授权企业范围；主管看所管理团队的授权成员；坐席保持自己的范围。主管/管理员本人的任务不可因人员框仅列坐席而消失，应保留独立“我负责的”入口或明确范围选项。离职/停用人员的历史金额不能仅因不再出现在活跃坐席选项中丢失，详见上一轮 BP01。

## 必须补的验收矩阵

- 管理员 / 主管 / 坐席，单团队 / 多团队 / 无成员 / 同名成员 / 未关联历史团队。
- 一组与十一组、团队重命名、坐席转组、负责人停用：按 ID 归属，不按名称子串。
- A 团队选人员 → B 团队：A 人员不残留；快速切换：迟到请求不覆盖 B。
- 篡改 group/person 组合：服务端拒绝或按明示契约收窄，不越权。
- 金额 → 对应任务 → 单任务详情 → 返回：团队、人员、指标、分页可解释且一致。
- 历史/当前/状态交叉切换；零结果须能看到生效条件，不误报无业务。
- 组别创建失败保留草稿；转交候选人刷新失效禁止旧目标提交；厂商切换不无提示继承不相容字段。
- 同范围、币种、查询口径下金额对应全量任务，不仅当前页；已关闭/取消未收余额仍可追踪。
